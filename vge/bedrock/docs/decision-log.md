# Журнал решений, попыток и результатов (Magma: Gecko + V8)

Зачем: чтобы не ходить по кругу. Каждая запись — что пробовали, чем мерили, что вышло, что решили.
Новые записи дописываются сверху раздела. Цифры — с этой машины. «Chrome» — Chromium 149
(V8 14.9.207.21) из playwright, на той же игре https://claybound-56949.web.app/.

Инструменты замеров: `tools/bench.py` (кадры, память, видеопамять; `--watch` действителен только
с окном на переднем плане), `tools/chromebench.mjs` (то же для Chrome, `CHROME_MEMDUMP=1` — дамп
memory-infra), `tools/chromeprofile.mjs` (профиль CPU Chrome), `tools/pgotrain.py` (сбор профиля PGO).

## Решения пользователя (общие)

- Порядок: сначала паузы GC, потом звук, потом «всё остальное»; интеграция по типу CEF — последней.
- Названия: Magma — runtime на Gecko + V8 и его встраивание по типу CEF (одно целое); Bedrock — обвязка
  для нативных приложений; Мегабраузер — будущий браузер. Идентификаторы в коде не переименовываем.
- V8 не правим без нужды («V8 работает в Chrome»), работаем на стыке.
- Ничего не откатывать без слова пользователя, включая свои эксперименты.
- Метрика памяти, по которой судит пользователь, — столбец «Память» в диспетчере задач (private working set).
- 2026-11-17: «Видеопамять» — следующая задача после GC и звука.
- 2026-11-17: «Да, делай» — оптимизированная сборка V8 (PGO на нашей нагрузке + ThinLTO).

## Открытые вопросы к пользователю

- Сводить D3D11-устройства в одно, как в Chrome (WebGL на устройстве композитора)? Цена — WebGL и
  WebRender перестают идти параллельно. См. «Видеопамять».
- Переводить structured clone на `v8::ValueSerializer`? Меняет формат буфера (данные IndexedDB,
  сохранённые нашим же рантаймом). См. «postMessage».
- Убирать ли 4 неэффективных эксперимента в V8 (коммит 5661c20c3f3: условие завершения по IsIdle,
  публикация барьера на каждом шаге, предварительная маркировка retained maps, маркировка активного
  suspender'а)? Пока оставлены.
- Незакоммиченная диагностика VGECLEARLISTS в V8 `mark-compact.cc` — не тронута.

## Сборка V8: PGO и ThinLTO (2026-11-17)

Почему: старт игры упирается в C++-рантайм V8 (см. «Рывок старта»). Chrome собирает V8 с PGO,
ThinLTO и PGO builtins, у нас был только `-O3`.

Попытки:
- Проверка флагов сборки: `dcheck_always_on=false`, `is_debug=false`, slow dchecks и verify heap
  выключены. Отладочных замедлителей нет. V8 уже собирается `optimize_speed` (`/clang:-O3`), так что
  `is_official_build` почти ничего не добавил бы.
- PGO на clang 24 из Chromium: отказ. Сырые профили версии 11, а `llvm-profdata` у нас только LLVM 22
  (читает до 10); нужный пришлось бы скачивать. Сборка остановлена.
- V8 собран clang 22 из `~/.mozbuild/clang` (тот же, что у Gecko): собирается без ошибок. Это же
  открывает ThinLTO вместе с xul.
- Фаза 2 PGO упала: конфиг всегда требует `chrome/build/win64.pgo.txt`. Решение — пустой файл в
  checkout V8.
- Профиль снят на 6 прогонах (игра ×2, runtime.html, three.html, clone.html, jsspeed.html). Профили
  второго процесса битые (его убивают при выходе) — пропускаются.

Результат PGO (медиана 5; -O3 → PGO → Chrome):
- компиляция и первый запуск 400 функций: 5 → 3 → 2,4 мс;
- JSON 20000 объектов: 19–20 → 11 → 12 мс;
- строки: 21–22 → 14–15 → 13,7–16,7 мс;
- смена форм объектов: 3 → 1 → 0,6 мс;
- three.js (updateMatrixWorld, нормали, рейкаст): без заметной разницы (шум);
- самый длинный кадр старта игры: 825–892 → 775–850 мс (у Chrome 570).

Решения: V8 собирается clang 22 с PGO по нашему профилю. Процедура — `docs/v8-pgo.md`.
Профиль — `C:/Projects/v8-build/pgo/v8.profdata`. Прежняя библиотека сохранена как
`dist/Lib/Win64MD/wee8.release-clang24.lib`. ThinLTO — в работе.

## Рывок старта игры (first_frame_ms) (2026-11-17)

Метрика: `first_frame_ms` в bench — самый длинный кадр за первые 5 секунд, а не время до первого кадра.
Было 758–925 мс, у Chrome 570.

Попытки и что исключено:
- Профиль Gecko: длинный кадр — JS игры (setTimeout / обработчик postMessage от воркера). Нативные
  стеки обрываются на JIT-кадрах V8 (из 186 выборок полные 14).
- Синхронные вызовы WebGL: в одном прогоне `GetFrontBuffer` ждал 448 мс, а `GetLinkResult` — 227 мс
  на 40 программ. В другом прогоне поток хоста WebGL простаивал, а главный поток считал JS. Не причина.
- GC: за первые 6 с паузы главного изолята 59 мс (62 scavenge = 38 мс, 4 mark-compact = 21 мс), у
  Chrome 47 мс. Не причина.
- Процессор: в длинном кадре главный поток получил 742 мс CPU из 752 мс по часам. Он не ждёт, а
  считает.
- Тиринг JIT: three.js в чистом виде на холодную и прогретый у нас медленнее на 5–22%. Тиринг в
  порядке.
- Математика: `Math.sin/acos/exp/hypot` у нас в 2,4–2,7 раза медленнее. Причина — V8 15.7 после ветки
  14.9 перешёл на точную llvm-libc (коммиты bc40c180447, e5bb55463b5, 8787f0842a1, май 2026). Это
  ~3% тиков старта. V8 не трогаем.
- Сравнение по функциям (`chromeprofile.mjs` против `--prof` V8): функции игры у нас в 2–4 раза
  дольше, но тики V8 на Windows грубые (раз в 15–30 мс).
- Рантайм V8 (компиляция, IC, JSON, строки) у нас в 1,4–2 раза медленнее Chrome → сборка V8 (см. выше).

Итог: PGO снял разрыв в рантайм-тесте, но рывок старта уменьшился лишь до 775–850 мс. Остаток пока
не объяснён.

## postMessage / structured clone (2026-11-17)

Тест: воркер строит 20000 объектов `{name, position{x,y,z}, scale[3], flags{}, data: Float32Array(8)}`
и отдаёт их через postMessage (`bench/jsweb/clone.html`).

Было: сериализация в воркере 362–487 мс, чтение ~174 мс (Chrome ~20 и ~20).

Причина (профиль): `classify` вызывал `ObjectFromV8` на каждый объект и создавал управляемую
Gecko-ячейку (форма, private key, persistent handle). Для каждого typed array ячейка заводилась ради
типа элементов. Чтение создавало typed array через ячейки.

Сделано (коммит c932ec056f): объект без ячейки классифицируется прямо по V8; тип typed array берётся
из V8 (`ScalarOf` теперь знает Float16Array); чтение создаёт typed array конструкторами V8; память
обратных ссылок — один поиск вместо двух.

Результат: сериализация 214–241 мс, чтение ~120 мс. Проверка `clonecheck.html` (все виды typed array
со смещениями, общий буфер, DataView, Map, Set, Date, RegExp, BigInt, обратные ссылки) — совпадает.
Рывок старта игры не изменился: postMessage его не определяет.

Остаток: накладные расходы API V8 на каждый объект (`GetOwnPropertyNames`, `HasOwnProperty`, `Get`,
хеш идентичности). Догнать Chrome можно только через `v8::ValueSerializer` — вопрос к пользователю.

## Видеопамять (2026-11-17)

Было 563–578 МБ, у Chrome 323 МБ (одна и та же игра).

Сделано:
- WebRender (коммит 9e8bd10ca6): общие поверхности render task graph по нужному размеру вместо всегда
  2048, пул render target отпускает цели, простаивающие 60 кадров. Видеопамять → 500 МБ, пул 56–72 → 0–3 МБ.
- WebRender (коммит 12f39839d3): атласы текстурного кэша начинаются с 512 и растут по объёму
  содержимого; атлас 1024 — одна колонка; общие поверхности округляются по ширине и высоте отдельно.
  Цветные глифы 2048 → 512, обычные глифы 2048 → 512/1024. Видеопамять → 458 МБ.
- WebRender (коммит bd3146edb0): атлас уменьшается вдвое, когда содержимое помещается (заполнение
  ≤ 90% половинного, все элементы влезают). Меньшая текстура создаётся на кадр раньше первого
  копирования, иначе падение: копирования выполняются до создания текстур в пакете обновлений.
  Атлас картинок 2048 → 1024 после пика, ресурсы GPU 343 → 335 МБ.

Отвергнуто:
- Отпускать лишний буфер в корзине переиспользования WebGL (простой 60 кадров): буфер тут же
  создавался заново, запас нужен на неровных кадрах. Правка убрана. У Chrome (`drawing_buffer.cc`)
  на Windows запас до 4 буферов (scanout) — у нас не больше.
- Убрать контентное D3D11-устройство: на нём Direct2D и canvas 2D; без него canvas уйдёт на процессор.

Анализ остатка (GPU-трасса 346 МБ против 458 МБ по счётчику Windows):
- ~245 МБ — ресурсы игры в WebGL (текстуры с мипами 143, рендер-таргеты 81, буферы 11) — задаются
  игрой, у обоих через ANGLE;
- наша служебная часть ~95 МБ против ~64 МБ у Chrome (shared images 33, Skia 19, cc 12 по memory-infra);
- ~112 МБ вне ресурсов D3D11: три D3D11-устройства (WebGL, композитор, контент), каждое ~11 МБ
  (замер отдельным тестом), плюс внутренние буферы ANGLE каждого и цепочки показа. В Chrome всё на
  одном устройстве ANGLE.
- ANGLE в нашей сборке: `ANGLE_ENABLE_CONTEXT_MUTEX` + `SHARE_CONTEXT_LOCK`, у разных групп разные
  мьютексы, а бэкенд D3D11 держит одно состояние на устройство (`Context11::onMakeCurrent`). Значит,
  общее устройство требует одного потока GPU (как в Chrome) или общей блокировки — ждёт решения.

## Закрытие окна (2026-11)

Падение в `nsHttpChannel::AsyncOpenFinal` (страница грузилась во время остановки classifier) и
зависание примерно 1 из 3 (цикл GC при остановке воркеров с отложенными задачами). Исправлено
(коммит 103cb9ee99): фазы остановки через `AppShutdown::AdvanceShutdownPhase`, синхронный полный GC не
ставит последующие задачи. 8/8 чистых выходов за ~0,25 с.

## Паузы GC (2026-11)

Было ~20 мс, Chrome — медиана 0,77 мс (максимум 4,3).

Сделано: одинарная маркировка managed-ячеек; внешние строки V8 поверх ячеек; anchored-ячейки через
TracedReference + prefinalizer; атомы собираемые через weak handles; конкурентная серая маркировка в V8
с отложенным переокрашиванием семян в фоновом построителе (коммиты 551cafe7cca, 5661c20c3f3 в V8;
7cfd5bf1c1 в Gecko); per-thread буфер серых якорей вместо мьютекса.

Опровергнуто данными (причиной не были): корни пролога Gecko, барьеры внутри GC (0), handle scopes (0),
новые сильные глобальные (+1–4), retained maps, публикация барьера, корень suspender, эфемероны.
Настоящая причина: чёрная маркировка паузы доходила до серых объектов через обычные объекты
(PropertyArray → JSFunction, SourceTextModule, Map).

Ошибки метода (не повторять):
- диагностика `count_work` вызывала `Publish()` и меняла поведение — ложное «исправлено»;
- логи смешивали изоляты воркеров с главным;
- прогоны шли одновременно с хостами другой сессии — ссылки линковки падали, taskkill закрывал чужие окна;
- замеры `--watch` с перекрытым окном недействительны;
- мьютекс в TraceGray давал конкуренцию (mark 2,82 мс).

Результат: медиана 3,6–4,1 мс; closure 1,2–2,8 → 0,26–0,41 мс; mark 1,20 мс. Остаток (evacuate
~1,3–1,7, clear ~0,65–0,87 мс) — внутренняя работа V8. Глобальные хендлы 25,8 тыс. → ~15 тыс.
